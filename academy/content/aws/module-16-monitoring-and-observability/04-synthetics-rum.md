# CloudWatch Synthetics, RUM, and ServiceLens

## Overview

The previous three lessons covered reactive observability — metrics, logs, and traces that describe what your system is doing. This lesson covers the proactive and user-perspective layers: synthetic monitoring that tests your endpoints before users reach them, real user monitoring that measures what actual users experience in their browsers, and ServiceLens that brings metrics, logs, and traces together in a single operational view.

CloudWatch Synthetics runs scripted canary checks on a schedule — simulating a user logging in, searching for a product, or calling an API — and alerts when the simulation fails. This catches issues that CloudWatch alarms miss: a working backend that returns correct responses but serves a broken JavaScript bundle, a checkout flow that succeeds for most users but fails for a specific payment method, or an API that responds with 200 but with corrupted response bodies. CloudWatch RUM collects real browser performance data — page load time, JavaScript errors, Core Web Vitals — from actual users across their actual devices, geographies, and network conditions. ServiceLens connects everything: the X-Ray Service Map alongside CloudWatch metrics and logs for each service, in one interface.

For the SAA exam, understand the purpose and runtime of Synthetics canaries, the distinction between Synthetics (scripted, proactive) and RUM (real users, passive), and what ServiceLens unifies. SAP adds canary scripting, RUM session data, and how to build SLO tracking using metric math in CloudWatch dashboards. After this lesson, you will be able to design the proactive and user-experience layers of an observability stack.

## Core Concepts

### CloudWatch Synthetics Canaries

A **canary** is a scheduled script that tests an endpoint or workflow from the outside, the way a real user would. CloudWatch Synthetics runs canary scripts as Lambda functions — Node.js or Python — on a configurable schedule (as frequent as every minute).

Canaries work at two levels. **API canaries** make HTTP requests to an endpoint, validate the response code and optionally the response body, and record latency. These are the simplest form — a health check that runs on a schedule. **Visual or browser canaries** use headless Chromium (via Puppeteer in Node.js) to navigate a real web page, interact with page elements, and validate that a workflow completes correctly. These simulate exactly what a user does: click a button, fill a form, assert that a confirmation message appears.

CloudWatch Synthetics provides **blueprints** — pre-built canary templates for common patterns: heartbeat monitoring (basic HTTP check), API canary (single API endpoint validation), broken link checker (crawl a page and verify all links return 200), visual monitoring (screenshot comparison), and Canary Recorder (record a browser session and replay it as a canary script).

Failed canaries publish metrics to CloudWatch (`SuccessPercent`, `Duration`) and can trigger CloudWatch Alarms, which in turn can notify via SNS or trigger automated remediation.

Canaries can run inside your VPC — useful for testing internal endpoints not accessible from the public internet. The Lambda function running the canary must have network access to the endpoint it tests.

### CloudWatch Real User Monitoring (RUM)

**RUM** collects performance data from actual user browsers. You add a small JavaScript snippet generated by CloudWatch RUM to your web pages — it loads asynchronously and captures: page load timing (DNS, TCP, server response, DOM render), JavaScript errors, HTTP request performance for every XHR and fetch call, and **Core Web Vitals** (Largest Contentful Paint, First Input Delay, Cumulative Layout Shift — the Google-defined metrics that directly predict user experience quality).

The critical distinction from Synthetics: RUM measures what real users actually experience. A canary runs from an AWS data center with high bandwidth and zero network jitter. Real users connect from mobile devices in Thailand, behind corporate proxies in Germany, on slow 4G in rural areas. RUM surfaces the user-experience gaps that are invisible in synthetic testing — a page that loads in 1.2 seconds in your canary but takes 7 seconds for mobile users in Southeast Asia.

RUM aggregates anonymized session data. You can filter and segment it by browser, operating system, country, page, and performance tier. CloudWatch RUM integrates with X-Ray — if a page load makes API calls and those calls are traced with X-Ray, you can navigate from a slow RUM session to the X-Ray trace for those API calls.

### CloudWatch ServiceLens

**ServiceLens** is a CloudWatch feature that integrates X-Ray's Service Map with CloudWatch metrics and logs, creating a unified operational view per service. Rather than switching between the X-Ray console, CloudWatch metrics, and CloudWatch Logs Insights to investigate an issue, ServiceLens presents all three in one interface with pre-filtered, contextually relevant views.

When you click a node in the ServiceLens Service Map, you see: health indicators (error rate, latency), relevant CloudWatch metric graphs, a list of CloudWatch Logs log groups associated with that service, and links to X-Ray traces filtered to that service. The experience compresses a typical on-call investigation — from alert to root cause — by eliminating the manual steps of navigating to each tool, selecting the right time range, and filtering to the relevant service.

ServiceLens also provides **transaction search** — find all traces from the past time window that match a filter (status = 5xx, annotation userId = specific user), examine the full trace timeline, and navigate directly to the related CloudWatch log events that occurred at the same timestamp.

### SLOs and Error Budgets with CloudWatch

A **Service Level Objective (SLO)** is a measurable reliability target — "99.9% of requests succeed," "p99 latency under 500ms." CloudWatch does not have a native SLO feature, but you can implement SLO tracking with **metric math** in dashboards.

Calculate a success rate: `100 * (1 - ErrorCount/RequestCount)`. If this value drops below 99.9%, the SLO is violated. Track this as a dashboard widget with a threshold line at 99.9%.

An **error budget** is the allowed failure rate over a period: for a 99.9% monthly SLO, you have 0.1% × 43,200 minutes = 43 minutes of downtime allowed per month. As the error budget burns, you reduce risk — pause deployments, do postmortems, defer new features until reliability is restored.
