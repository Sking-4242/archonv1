# S3 Versioning and Object Lock

## Overview

S3 Versioning is a bucket-level feature that preserves every state an object has ever been in. When versioning is enabled, no write to an existing key destroys the previous data — instead, S3 creates a new version with a unique version ID and the previous content remains retrievable by its own version ID. Deletions do not destroy data either; they create a delete marker, a lightweight pointer that makes the object appear gone to clients that do not specify a version ID. The previous content is still in the bucket, waiting to be recovered. Versioning is the foundational data protection mechanism for S3 and is a prerequisite for several more advanced features.

Versioning exists because the most common way data is lost in object storage is not hardware failure — it is human error. A developer runs a script that overwrites 1,000 files with incorrect data. A misconfigured automated process deletes a month of records. A ransomware attack encrypts every object in a bucket by PUTting encrypted versions over the originals. Without versioning, these events produce permanent, unrecoverable data loss. With versioning, every overwrite and every deletion is reversible, because the original content exists as a previous version. S3's durability guarantees protect data from hardware failure; versioning protects data from logical corruption.

For the SAA-C03 exam, versioning unlocks questions about data protection architecture, compliance storage, and Object Lock. You need to understand not just that versioning prevents data loss, but how the version ID system works, what a delete marker is, how MFA Delete adds an extra layer of protection against malicious deletion, and how Object Lock extends versioning into provably immutable WORM storage for regulated industries. These concepts appear together in scenario questions where a student must select the correct combination of features to satisfy a compliance requirement.

## Core Concepts

### How Versioning Works: Version IDs and Object State

When you enable versioning on a bucket, every object stored in that bucket acquires a version ID — a unique string generated by S3 (for example, `Lyi7p5BOFaEtxG7K9TUJAhT9YZzUPHpN`). When you PUT to an existing key, S3 does not overwrite the data. It creates a new version with a new version ID and marks that version as current. The old version retains its original version ID and remains stored. A GET on the key without specifying a version ID returns the current (most recently PUT) version. A GET specifying an old version ID returns that exact historical version.

Before versioning is enabled, any object in the bucket has a version ID of `null`. When versioning is enabled, new PUTs generate real version IDs, but the pre-existing objects retain their `null` version ID. If you PUT to a key that previously had a `null`-versioned object, the `null` version is preserved as a noncurrent version and the new PUT creates the current version with a real version ID.

Versioning states are: Unversioned (default, never enabled), Enabled, and Suspended. Once enabled, versioning cannot be fully disabled — you can only suspend it. In the Suspended state, new PUTs create or overwrite the `null` version (without creating additional versions), but all previously created versions with real version IDs are preserved. Suspension is used when you want to stop accumulating new versions temporarily while retaining history.

### Delete Markers: Soft Deletion

When versioning is enabled and you issue a DELETE on an object key without specifying a version ID, S3 does not delete any data. Instead, it creates a delete marker — a special zero-byte object version with a unique version ID and the `x-amz-delete-marker: true` metadata flag. The delete marker becomes the "current" version of that key. Any subsequent GET on the key without a version ID returns a 404, because the current version is a delete marker.

All previous data versions are still stored. To recover the object, you delete the delete marker (by issuing a DELETE that specifies the delete marker's version ID). When the delete marker is removed, the next most recent non-marker version becomes current, and the object reappears. To permanently delete an object and all its versions, you must issue a DELETE specifying each version ID individually — including the delete marker.

This design means that in a versioned bucket, a simple DELETE is always reversible. An attacker or an errant script that issues DELETE requests without version IDs leaves every object recoverable. The only irreversible operation is a DELETE that specifies a specific version ID — which is why MFA Delete exists to require human confirmation for those operations.

### Storage Costs and Lifecycle Management for Versions

Every version of an object is stored and billed as a complete object. A 500 MB file that is updated ten times consumes 5 GB of billable storage — each version is a full 500 MB copy, not an incremental diff. In a bucket where automated processes write new versions frequently, this can cause storage costs to grow faster than expected.

The solution is lifecycle rules scoped to noncurrent versions. A lifecycle rule with a `NoncurrentVersionTransition` action moves noncurrent versions to cheaper storage classes (Standard-IA, Glacier) after a specified number of days. A `NoncurrentVersionExpiration` action permanently deletes noncurrent versions after a specified number of days. A common pattern: keep the 5 most recent noncurrent versions by setting `NewerNoncurrentVersions: 5` in the expiration rule, so old history is pruned while meaningful recent history is retained.

Delete markers left behind when all versions have been deleted are called "expired delete markers." They consume no storage space but do appear in list operations and can accumulate. A `ExpiredObjectDeleteMarker: true` setting in a lifecycle rule automatically removes these orphaned markers.

### MFA Delete: Protection Against Malicious Permanent Deletion

MFA Delete is an optional S3 bucket configuration that requires a valid MFA token in addition to valid AWS credentials to perform either of two sensitive operations: permanently deleting a specific object version, or changing the versioning state of the bucket (enabling or suspending). Without MFA Delete, anyone with the correct IAM permissions can issue these destructive operations programmatically. With MFA Delete enabled, even a compromised set of AWS credentials cannot permanently destroy versioned data — the attacker would also need the physical MFA device.

MFA Delete has strict prerequisites. Versioning must be enabled on the bucket first. MFA Delete can only be enabled or disabled using the root account user's credentials (not an IAM user, not a role) combined with a valid root MFA token. It must be enabled via the AWS CLI (the Console does not support root-account MFA Delete configuration directly). Once enabled, every request to permanently delete a version or change versioning state must include the MFA serial number and current token as a request header.

The operational implication: if you enable MFA Delete on a production bucket, you must ensure your incident response runbook includes access to the root MFA device for any scenario where permanent version deletion is required. It should not be used casually — it adds meaningful friction to legitimate operations as well as malicious ones.

### S3 Object Lock: WORM Compliance at the Storage Layer

S3 Object Lock prevents object versions from being deleted or overwritten for a defined retention period or indefinitely. It implements Write Once Read Many (WORM) storage at the infrastructure level, not at the application or policy level. Object Lock is the mechanism AWS offers to satisfy regulatory requirements like SEC Rule 17a-4, FINRA, CFTC, and HIPAA that mandate tamper-evident, non-deletable record retention.

Object Lock must be enabled at bucket creation — you cannot enable it on an existing bucket after creation. Enabling Object Lock also enables versioning automatically and permanently (versioning cannot be suspended on an Object Lock bucket). Object Lock applies at the version level: you lock a specific version of an object for a retention period.

Two retention modes govern how strictly the lock is enforced. **Governance mode** allows users with the special IAM permission `s3:BypassGovernanceRetention` to override the lock and delete protected versions before retention expires. This is appropriate for organizations that want WORM semantics for normal operations but need the ability for privileged administrators to correct mistakes. **Compliance mode** is absolute: no user, no IAM permission, and not even the AWS root account can delete or overwrite a locked object version before the retention period expires. Compliance mode is required for regulatory mandates that do not permit even administrative overrides.

Retention periods can be set per-object at upload time using the `--object-lock-retain-until-date` parameter, or a default retention period can be configured at the bucket level and applied automatically to all newly uploaded objects. Legal hold is a separate mechanism that suspends expiration of a lock indefinitely regardless of the retention period — used during litigation holds where you cannot determine the needed retention duration in advance.

## Configuration Reference

### AWS CLI: Enable Versioning on a Bucket

```bash
aws s3api put-bucket-versioning \
  --bucket my-company-records \
  --versioning-configuration Status=Enabled
  # Status can be Enabled or Suspended; there is no Disabled option once enabled
  # Verify the current versioning state with:
aws s3api get-bucket-versioning --bucket my-company-records
```

### AWS CLI: List All Versions of Objects in a Bucket

```bash
aws s3api list-object-versions \
  --bucket my-company-records \
  --prefix "contracts/"
  # Returns a JSON object with Versions[] (all non-delete-marker versions)
  # and DeleteMarkers[] (all delete markers) for the given prefix
  # Each entry includes Key, VersionId, IsLatest, LastModified, and Size
```

### AWS CLI: Restore a Previous Version by Copying It to Current

```bash
# Method 1: Copy an old version back over the key (creates a new current version)
aws s3 cp \
  s3://my-company-records/contracts/agreement.pdf?versionId=Lyi7p5BOFaEtxG7K9TUJAhT9YZzUPHpN \
  s3://my-company-records/contracts/agreement.pdf
  # Copying an old version to the same key creates a new version that is
  # identical to the old version — the old version becomes noncurrent but is preserved

# Method 2: Delete the delete marker to un-delete a "deleted" object
aws s3api delete-object \
  --bucket my-company-records \
  --key contracts/agreement.pdf \
  --version-id <delete-marker-version-id>
  # Deleting the delete marker makes the previous non-marker version current again
  # Get the delete marker version ID from list-object-versions output
```

### AWS CLI: Permanently Delete a Specific Version

```bash
aws s3api delete-object \
  --bucket my-company-records \
  --key contracts/agreement.pdf \
  --version-id Lyi7p5BOFaEtxG7K9TUJAhT9YZzUPHpN
  # Specifying a version ID permanently deletes that specific version
  # With MFA Delete enabled, this requires --mfa "arn:aws:iam::123456789:mfa/root serial-number token"
```

### AWS CLI: Enable MFA Delete (Must Use Root Account)

```bash
aws s3api put-bucket-versioning \
  --bucket my-company-records \
  --versioning-configuration Status=Enabled,MFADelete=Enabled \
  --mfa "arn:aws:iam::123456789012:mfa/root-account-mfa-device 123456"
  # The --mfa parameter takes the MFA device ARN and the current 6-digit token
  # separated by a space; this must be the root account's MFA device
  # Only root can enable or disable MFA Delete — IAM users and roles cannot
```

### AWS CLI: Enable Object Lock and Set a Legal Hold

```bash
# Object Lock can only be enabled at bucket creation:
aws s3api create-bucket \
  --bucket my-compliance-archive \
  --region us-east-1 \
  --object-lock-enabled-for-bucket
  # --object-lock-enabled-for-bucket enables Object Lock AND versioning permanently

# Set a default retention period on the bucket:
aws s3api put-object-lock-configuration \
  --bucket my-compliance-archive \
  --object-lock-configuration '{
    "ObjectLockEnabled": "Enabled",
    "Rule": {
      "DefaultRetention": {
        "Mode": "COMPLIANCE",
        "Years": 7
      }
    }
  }'
  # All newly uploaded objects inherit this 7-year COMPLIANCE mode retention
  # Individual objects can override this with a longer (but not shorter) retention

# Apply a legal hold to a specific object version:
aws s3api put-object-legal-hold \
  --bucket my-compliance-archive \
  --key records/2024/trade-confirm-00123.json \
  --version-id <version-id> \
  --legal-hold Status=ON
  # Legal hold suspends retention expiration indefinitely regardless of the retention date
  # Requires s3:PutObjectLegalHold permission; remove with Status=OFF when hold is lifted
```

### Console Walkthrough: Enable Versioning

Navigate to **S3** in the AWS Console. Select your bucket. Click the **Properties** tab. Under **Bucket Versioning**, click **Edit**. Select **Enable** and click **Save changes**. The versioning status changes to "Enabled" immediately. Note: there is no option to "Disable" versioning — once enabled, your only option going forward is Suspend.

To view object versions in the Console: navigate to the bucket, click **Show versions** toggle in the object list. Each key expands to show all versions with their version IDs, modification dates, sizes, and whether each is the current version or a noncurrent version or delete marker.

## How to Decide

Use these criteria to determine the right combination of versioning features:

1. **Is any data in this bucket irreplaceable or difficult to recreate?** If yes, enable versioning. There is no downside beyond storage cost, and lifecycle rules mitigate cost. Enable versioning at bucket creation — you cannot retroactively version objects uploaded before versioning was enabled.

2. **Does the bucket have automated write workloads (CI/CD artifacts, logs, pipeline outputs)?** Configure `NoncurrentVersionExpiration` lifecycle rules to expire old versions after a defined number of days or keep only N most recent noncurrent versions. Without these rules, version accumulation will grow your bill rapidly.

3. **Do you need protection against malicious permanent deletion (not just accidental deletion)?** Enable MFA Delete. This requires root account access and an MFA device and adds operational friction — plan the runbook for legitimate delete operations before enabling it.

4. **Does the workload involve regulatory compliance mandating tamper-evident immutable storage?** Enable Object Lock at bucket creation. Choose Governance mode if privileged administrators need override capability; choose Compliance mode if the regulation absolutely prohibits any override. Consult legal/compliance to determine which regulations apply.

5. **Is the retention duration known upfront?** Set an Object Lock retention period per object at upload time or configure a bucket-level default. If retention duration is unknown (litigation hold), use legal hold instead — it suspends expiration until explicitly removed.

## How This Connects

- **S3 Lifecycle rules and versioning**: Lifecycle rules support separate actions for current vs. noncurrent versions, making it possible to keep current versions in Standard while transitioning old versions to Glacier and expiring them after a defined period. This intersection is a key exam topic.

- **AWS Backup and S3**: AWS Backup can vault S3 data with its own retention policies, but for per-object WORM compliance, S3 Object Lock is the native mechanism. Understanding when Object Lock vs. AWS Backup vault lock is appropriate requires knowing that Object Lock operates at the object level while Backup vault lock operates at the vault level.

- **CloudTrail and S3 data events**: Every PUT, DELETE, and version operation on an S3 bucket can be logged via CloudTrail data events. For Object Lock buckets under regulatory requirements, CloudTrail provides the audit trail showing who wrote, read, or attempted to delete each object version — pairing immutability with auditability.

- **IAM and the `s3:BypassGovernanceRetention` permission**: Object Lock Governance mode introduces a purpose-built IAM action that must be explicitly granted for administrators to override retention. This is an example of how S3 security extends beyond standard S3 actions and requires careful consideration of privilege when designing least-privilege IAM policies for compliance environments.

- **Replication and Object Lock**: S3 Cross-Region Replication can replicate Object Lock settings to destination buckets, preserving retention mode and retain-until dates on replicated versions. This allows you to maintain WORM compliance in a disaster recovery Region without re-applying locks manually.

## Exam Traps

**Trap 1: Versioning can be disabled once enabled.** Versioning has three states: Unversioned, Enabled, and Suspended. Once a bucket has had versioning enabled, it can never return to the Unversioned state. Suspending versioning stops creating new versions but preserves all existing versions. Exam questions that ask what happens when you "disable" versioning are testing whether you know Suspended vs. Unversioned behavior.

**Trap 2: Deleting an object in a versioned bucket permanently removes it.** A DELETE without a version ID creates a delete marker. The data is not deleted. Only a DELETE that specifies a version ID performs permanent deletion. This is the most tested versioning behavior on the exam — scenarios describe a deletion and ask what recovery options exist.

**Trap 3: MFA Delete can be enabled by any IAM administrator user.** MFA Delete can only be enabled or disabled by the root account user, using root credentials and the root MFA token. No IAM user or role has permission to change MFA Delete state, regardless of what IAM permissions they hold.

**Trap 4: Object Lock can be enabled on any existing bucket.** Object Lock must be enabled at bucket creation time. It cannot be retrofitted onto an existing bucket. If a compliance requirement is identified after a bucket is already in use, you must create a new bucket with Object Lock enabled and migrate the objects. This is a critical design point — enable Object Lock at the start for any bucket that will hold compliance-regulated data.

**Trap 5: Object Lock Compliance mode can be overridden by the root account.** Compliance mode is absolute — no user, no IAM policy, no AWS support action, and not the root account can delete or overwrite a Compliance-mode locked object before its retention period expires. Governance mode CAN be overridden by users with the `s3:BypassGovernanceRetention` IAM permission. Exam scenarios describing SEC 17a-4 or FINRA requirements should land on Compliance mode, not Governance mode.

## Summary

- S3 Versioning preserves every historical state of an object by assigning unique version IDs to each PUT, turning overwrites and deletes into recoverable events rather than permanent data loss.
- A DELETE without a version ID creates a delete marker that makes the object appear gone while all previous versions remain stored and retrievable; true permanent deletion requires specifying a version ID.
- Once versioning is enabled on a bucket, it can only be suspended — not disabled — and all existing versions are preserved regardless of suspension state.
- MFA Delete requires a valid MFA token to permanently delete object versions or change versioning state, protecting against compromised credentials enabling mass destruction; only the root account can enable MFA Delete.
- S3 Object Lock enforces WORM immutability at the storage layer — Governance mode allows privileged override, Compliance mode allows no override by anyone, and both require Object Lock to be enabled at bucket creation.
- Legal hold is a separate Object Lock mechanism that suspends retention expiration indefinitely for specific object versions, used when litigation hold duration is unknown at the time of application.

## Examples

A startup developer accidentally runs a script that overwrites 500 product description files in their S3 bucket with empty strings. With versioning enabled, each overwrite created a new empty-string version — but the previous content versions are still stored with their original version IDs. The developer uses `list-object-versions` to get the previous version IDs, then runs a restore script that copies each old version back over the current key, creating new current versions identical to the originals. The entire recovery takes 20 minutes. Without versioning, the data would have been permanently unrecoverable because S3 has no trash or recycle bin concept.

A healthcare company stores patient intake forms in a versioned S3 bucket and configures a lifecycle rule to keep only the 5 most recent noncurrent versions of any object and expire all noncurrent versions older than 180 days. A heavily revised intake form that is updated weekly does not accumulate years of history — only the current version plus the 5 most recent noncurrent versions are retained. This design balances compliance needs (recent audit trail) against cost (unbounded version accumulation is capped). The lifecycle rule targets noncurrent versions specifically, leaving the current version untouched regardless of age.

A publicly traded company must comply with SEC Rule 17a-4, which requires records to be unalterable and non-erasable for a defined period. They create an S3 bucket with Object Lock enabled in Compliance mode and configure a bucket-level default retention period of 7 years. Every record written to the bucket — regardless of who writes it or what tools are used — is automatically locked for 7 years. An IT administrator attempting to free disk space by deleting old records receives an access denied error even with full S3 admin permissions. An auditor requesting proof of immutability can point to the Compliance mode configuration as infrastructure-level enforcement, not merely a policy assertion — no code path, no privileged user, and no AWS process can bypass it.

## Think About It

1. Why does S3 implement deletion as a delete marker instead of actually removing the object when versioning is enabled? What problem does this design solve, and what new operational complexity does it introduce — particularly around storage costs and list operation results?

2. If every version of an object is stored and billed as a full copy, what would happen to your S3 bill if you enabled versioning on a bucket where a CI/CD pipeline writes a new build artifact every 10 minutes, 24 hours a day? How would you design lifecycle rules to control this without losing meaningful recovery history?

3. MFA Delete requires the root account to enable it, and using root credentials is generally considered a security anti-pattern in AWS. How do you reconcile the security recommendation to avoid root account usage with the requirement to use root to configure MFA Delete? What compensating controls reduce the risk of performing this root account operation?

4. Object Lock Governance mode allows privileged users to bypass retention. Under what business scenario would you choose Governance mode over Compliance mode? What risk are you accepting, and how would you document that risk for an internal audit?

5. What would happen if you restored an old version of an application configuration file that an application was actively using in production? How would you design a versioned S3 configuration workflow that safely promotes a previous version to current without causing a production incident during the promotion?

## Quick Check

**Q1.** In a versioned S3 bucket, what happens when you issue a DELETE request on an object key without specifying a version ID?

- A) The object and all its versions are permanently deleted
- B) The most recent version is permanently removed and the previous version becomes current
- C) A delete marker is placed on the key, making the object appear deleted while all versions are preserved
- D) The DELETE request is rejected with an error until a version ID is specified

**Answer: C** — Without a version ID, DELETE places a delete marker that becomes the current version and causes GETs on the key to return 404. All previous data versions remain stored and are recoverable by deleting the delete marker or specifying an old version ID directly.

**Q2.** Which S3 Object Lock mode prevents deletion even by the AWS root account before the retention period expires?

- A) Governance mode
- B) Compliance mode
- C) Legal Hold mode
- D) Strict mode

**Answer: B** — Compliance mode enforces the retention period absolutely with no override capability for any user including root. Governance mode allows users with the `s3:BypassGovernanceRetention` IAM permission to override. Legal Hold is a separate feature that suspends expiration but is not a retention mode. "Strict mode" does not exist in S3.

**Q3.** What is the key cost consideration when enabling S3 Versioning on a bucket where objects are updated frequently?

- A) Versioning doubles API call costs for every PUT and GET operation
- B) Each version is stored and billed as a full independent object, multiplying storage costs proportionally to update frequency
- C) Versioned buckets cannot use lifecycle policies to control cost
- D) Versioning incurs a per-version metadata fee charged separately from storage

**Answer: B** — Every version of an object is billed as a complete stored object at the full object size. A 1 GB file updated 10 times consumes 10 GB of billable storage unless lifecycle rules expire noncurrent versions. Lifecycle policies work on versioned buckets and are the primary tool for controlling version storage cost.
